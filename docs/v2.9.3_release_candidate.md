## What physics *really* does now

- Speed and entry angle influence the carry factor. Revs and entry angle also determine *lateral ball deflection through the pins*.
- The lane's oil level, shot line/boards, transition and hook determine where the ball arrives at the pocket/target.
- A shot samples each pin **front to back**. The ball may touch it directly; already falling adjacent pins can transfer energy one or two rows further back. A distant, disconnected pin has only a tiny chance of falling as an incidental rebound.
- A high-quality pocket contact can trigger energetic carry, but **does not automatically award all ten pins**. It still requires contact and a pin-to-pin chain to clear the rack. The 7–10 remains a very difficult conversion.
- Spare deliveries target the nearest forward standing pin and use the plastic spare ball. Two-pin same-row baby splits use a gap target; distant 7–10-style splits do not. The 0/ full-rack case never takes the first-ball strike branch.
- Every shot publishes the *actual knocked-down pins* and their chronological contact order to the front, overhead and left hero cameras. The renderer does not use the game RNG.
- This is a lightweight, seeded, physics-informed tenpin model, **not** a real rigid-body 3D simulator. More detailed real-world trajectories would require another implementation and calibration campaign.

### Snapshot compatibility

- New matches are explicitly stamped `physics_version=2.9.3`.
- Matches saved as `2.9.0` use frozen `services/legacy_v290_pin_engine.py` **and** `services/legacy_v290_impact_model.py`, so their remaining throws retain the old physics and RNG sequence.
- Unversioned/pre-v2.9.0 matches use the existing `2.8.5t` frozen engine.
- A tournament roll-off also selects the same frozen model as its originating saved match. Neither past frame scores nor completed career records are recalculated.

## Automated release checks

Run with Python 3.13 and `requirements.txt`:

```bash
python -m compileall -q bot.py cogs services storage models ui
python -m unittest discover -s tests -p 'test_*.py' -v
python -m services.release_audit
python -m services.v293_rc_audit 500
python -c "from services.asset_validation import validate_broadcast_assets; print(validate_broadcast_assets(strict=True))"
```

`v293_rc_audit` checks 10,000 complete games (500 seeds × 5 oil patterns × 4 skill levels), legal pin-state/set invariants, realistic scoring range, lane sensitivity, **mid-game snapshot replay**, handedness variation, pinned contact orders and scoring; tests additionally cover unconnected split leaves, controlled oil/ball/board/angle/speed/revs changes, three-camera fall progress, tenth-frame and 0/ rules, SQLite WAL backups, deliberate mid-finalisation failure, retry deduplication and Undo. CI runs unit discovery, release audit, compile checks and a quicker 2,000-game RC physics gate; a separate longer report accompanies the release package.

## Deployment blockers still requiring the user's beta Discord server

These steps cannot be certified by source review, generated fallback art or a fake Discord channel. They require a configured Discord bot, a staging server with permissions and **the real asset files**.

1. Preserve production `data/`, make and verify a SQLite backup; keep your PNG assets intact. Install the code onto a **separate staging service/database**, not the active competition bot.
2. Install the existing 941×1672 hero lane, 1254×1254 overhead/pit plates, all pin sprites, 10 ball sprites and both five-frame bowler sets at their unchanged paths. Run `validate_broadcast_assets(strict=True)` and set `REQUIRE_PRODUCTION_ART=1`. A clean overhead plate without old 5–3–2 circles is strongly preferred.
3. On mobile **and desktop** check all 4–3–2–1 overhead pins align to the intended circles; verify pit/front pin order, bowler scale, ball emergence, 23-frame playback and the same downed pins visible in all three cameras on first, second and tenth-frame deliveries. Inspect optional `cheer.png` separately.
4. Run a **manual 2-bowler match** through normal frames, 0/, strike-spare, tenth-frame X9/, 9/X and XXX. Then repeat with Auto Play. Check stage commentary doesn't reveal the outcome early and every menu/control returns to the proper home view.
5. Run a **round-robin draw**, a tied knockout requiring sudden death, a best-of-three series and final bracket advancement. Confirm each fixture, career award, achievement, rank and record is written exactly once.
6. Interrupt a match mid-frame; restart and restore; confirm the same ball, pin leave and lane. Exercise Undo once, repeated Undo and replay after Undo. Interrupt **postgame** publication and retry finalisation without duplicate game/XP/honours. Verify an older v2.9.0 snapshot still replays under its old simulation.
7. Check ordinary users cannot invoke Director / result corrections / manual awards. Check Admin Home, Director and public records navigation and client component limits.
8. Measure GIF attachment sizes, Discord rate limits and actual slow-client replay, then record a staging sign-off with screenshots and a full log before public deployment.

**Unverified until completed:** live guild interactions, real PNG alignment and performance on the user's production-sized asset pack. These are not silently marked passed.

## Rollback

Use the database copy made **before installation** if a schema/storage problem occurs; do not replay committed results into an older database. Switch the deployed code back to v2.9.2, restore the corresponding database backup only when needed, and keep the original asset tree. Do not force-push GitHub or replace the live DB without checking for results recorded after the backup.

## Shipping decision

**Code RC** is acceptable when the automated test suite, crash/recovery gates and production-art preflight pass. **Public release** remains blocked until the real-art and Discord staging acceptance steps above are completed and recorded. This package is not automatically pushed to GitHub.
